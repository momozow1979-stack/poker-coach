# カメラ・ハンド読み取り 仕様（ライブ実卓）

ハンドレビューの入力を、**カメラで撮った実卓の写真から自動で下書きする**機能の設計。
ライブ（物理テーブル）を対象とし、ガイド枠に合わせて撮らせることで読み取り精度を上げる。

> **重要（AGENTS.md ルール 2）**: OpenAI の API キーはアプリに埋め込まない。
> Vision の呼び出しは必ず Supabase Edge Function（サーバー側）から行う。写真も Edge Function
> 経由でモデルに渡す。クライアントコードにキーを置かない。

## 0. 位置づけ（できること / できないこと）

- **カメラ = 入力の自動下書き**であって、全自動レビューではない。
- 1 枚の写真から確実に読めるのは**カードだけ**。ポジション・有効スタック(BB)・各ストリートの
  アクション履歴（誰がベット/レイズ/フォールドしたか、サイズ）は写真に写らないため、
  **ユーザーが入力**する。カメラはあくまで `HandReviewInput`（`lib/features/hand_review/domain/hand_review_input.dart`）の
  カード欄をプリフィルする。
- 読み取り結果は**必ずユーザーが確認・修正してからレビュー実行**する。誤読を黙って流さない
  （AGENTS.md ルール 1「捏造させない」と同じ思想）。

## 1. 撮影フロー（ガイド枠つき・分割撮影）

画面に**位置合わせ用のオーバーレイ枠**を出し、そこにカードを合わせて撮らせる。
枠に合わせることで画角・傾き・写り込みが安定し、Vision の読み取り精度が上がる。

| スロット | 枠 | ショット | 備考 |
| --- | --- | --- | --- |
| 自分の手札 (`hero_hand`) | 2 枚枠 | 単独 1 ショット | 常に撮る |
| フロップ (`flop.board`) | 3 枚枠 | 単独、または相手ハンドと同時 | 下記参照 |
| ターン (`turn.card`) | +1 枚枠 | ストリート進行に合わせ単独 | 分割撮影 |
| リバー (`river.card`) | +1 枚枠 | ストリート進行に合わせ単独 | 分割撮影 |
| 相手ハンド (`villain_hand`) | 2 枚枠 | ショーダウンで見えた時のみ | フロップと同時撮影可 |

- **分割撮影を基本**にする。ライブはフロップ→ターン→リバーと 1 枚ずつ増えるので、
  ストリートごとに撮るのが自然で、まとめて撮るより誤読が少ない。
- **フロップ＋相手ハンド（オープン時）の同時撮影**に対応する。この場合オーバーレイを
  **「ボード」枠と「相手」枠の 2 ゾーン**に分け、どちらがボードでどちらが相手かを
  ユーザーにもモデルにも明示する（誤割り当て防止）。撮影後、各ゾーンを別スロットとして
  `/read-hand` に渡す。
- 各ショットは**撮り直し可**。読み取り後の確認画面からも撮り直せる。

## 2. 読み取りパイプライン

```
写真(1ゾーン=1スロット分) + スロット種別
  → POST /read-hand   （Edge Function。OpenAI Vision をサーバー側で呼ぶ）
  → { slot, cards[], confidence[], warnings[] }
  → HandReviewInput の該当カード欄にプリフィル
  → 確認画面（低信頼度をハイライト）→ ユーザー確定
  → 既存 POST /review へ
```

- 送信は**1 ゾーン = 1 スロット分**を基本にする（hero / flop / turn / river / villain）。
  同時撮影したフロップ＋相手ハンドは、クライアントで 2 リクエスト、または 1 リクエストで
  2 ゾーンを渡す（実装簡単さから当面は 2 リクエスト推奨）。
- OpenAI は Vision 対応モデル（例: gpt-4o 系）を Structured Output で使う。

### 2-1. `/read-hand` 入力

`multipart/form-data`（画像バイナリ）または base64 JSON のいずれか。スロット種別を必ず添える。

```json
{
  "slot": "flop",          // hero | flop | turn | river | villain
  "expected_count": 3,     // hero/villain/flop=... 期待枚数（検証に使う）
  "image": "<base64 or multipart>"
}
```

### 2-2. `/read-hand` 出力（Structured Output で固定）

```json
{
  "slot": "flop",
  "cards": ["Qs", "7d", "2c"],
  "confidence": [0.98, 0.95, 0.70],
  "warnings": []
}
```

- `cards` は `PlayingCard.parse`（`lib/shared/models/playing_card.dart`）が受け付けるコード
  （ランク `A K Q J T 9..2` + スート `s h d c`。例 `Ah`, `Js`, `Qs`, `7d`, `2c`）。
- `confidence` はカードごと（0.0〜1.0）。**自信が無い時は捏造せず低信頼度で返す**。
  枚数が読めない/欠ける時は、その位置を返さず `warnings` に理由を入れる。
- `warnings` は人間可読の日本語メッセージ配列（例: 「3 枚目が反射で読めませんでした」）。

## 3. Vision プロンプト設計（`/read-hand`）

System Prompt（要点。キーはサーバー側で付与）:

```
あなたはトランプ（ポーカー）のカードを画像から読み取る認識器です。
- 画像内のプレイングカードのランクとスートだけを読み取る。
- 出力はランク(A,K,Q,J,T,9,8,7,6,5,4,3,2)とスート(s=スペード,h=ハート,d=ダイヤ,c=クラブ)の
  2文字コード（例: Ah, Ts, 7d）。
- 読み取れないカードは推測で埋めない。自信が低い場合は confidence を下げて返す。
- 指定された slot の期待枚数を超える/不足する場合は warnings に理由を書く。
- 出力は指定 JSON スキーマのみ。カード以外（チップ額・人物等）は読み取らない。
```

- 出力は 2-2 のスキーマに Structured Output（`response_format` の JSON Schema）で固定する。
- ランク `10` は `T` に正規化する。

## 4. 確認ステップ（必須・誤読を流さない）

- 読み取り結果を既存のカードピッカー（`lib/features/hand_review/presentation/widgets/card_picker_sheet.dart`）
  と `card_slot_row.dart` にプリフィルする。
- **低信頼度（例: confidence < 0.9）のカードはハイライト**し、タップ確認するまで
  レビュー実行ボタンを無効にする。
- カメラで埋まらない項目（ポジション・有効スタック・各ストリートのアクション・相手傾向・
  ゲーム種別）は従来どおりユーザーが入力する。
- **自動でレビューを実行しない。** ユーザーがフォーム全体を確認して初めて `/review` に送る。

## 5. バリデーション

- 全スロット合算で**カード重複を禁止**する（既存の `HandReviewInput.usedCards` を利用）。
  重複を検出したら該当カードを未確定扱いにして確認を促す。
- 不正コード（存在しないランク/スート、`T` 以外の 2 桁など）は破棄して `warnings` 化。
- スロットの期待枚数（hero=2, flop=3, turn=1, river=1, villain=2）と不一致なら確認を促す。

## 6. 権限・プライバシー

- カメラ権限（iOS: `NSCameraUsageDescription` / Android: `CAMERA`）を追加する。
- 画像は Edge Function 経由で OpenAI に送る。**原則として画像は保存しない**
  （読み取り後は破棄）。保存が要る場合は別途ユーザー同意と設計を行う。
- 送信するのはカード読み取りに必要な画像のみ。個人が特定できる背景等は極力枠外にするよう
  撮影ガイドで促す。

## 8. スコープ / 段階

- **MVP**: 自分の手札・フロップ（＋見えていれば相手ハンド）をガイド枠で撮影 → `/read-hand` →
  確認画面でプリフィル → 既存 `/review`。ターン/リバーは手入力でも可。
- **次段階**: ターン/リバーの分割撮影、読み取り精度に応じた再撮影導線、
  （将来）オンラインのスクリーンショット対応でスタック/ポジションまで自動入力。

## 9. 未決事項

- confidence のしきい値（初期案 0.9）は実測で調整する。
- 同時撮影（フロップ＋相手）を 1 リクエスト 2 ゾーンにするか 2 リクエストにするかは、
  実装時に精度と手数で判断（当面 2 リクエスト）。
- 使用する OpenAI モデル ID とコスト見積もりは実装フェーズで確定する。
